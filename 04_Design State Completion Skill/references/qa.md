# QA Rules

<!-- scope: 交付前 QA checklist + 高频失败模式 + 失败最小修复 -->

## 原则

QA 不能只写“通过”。写入型任务交付前必须保留可复核证据：参考源、生成结果、问题清单和清零结论。

问题清单非空时，不得最终回复“已完成”。

## 1. 推演与矩阵 QA

- 是否完成对象层级判断：页面级 / 模块级 / 子结构级 / 字段级。
- 矩阵主轴是否来自目标对象变量，而不是画面文案差异。
- 用户要求补子结构全情况时，矩阵主轴是否对齐该子结构内部变量。
- 每个状态是否有触发条件、用户含义、页面变化、主 CTA、生成方式、是否画稿和假设说明。
- 是否过滤非法组合和低价值组合，并说明原因。
- 是否区分业务状态和异常状态。

## 2. 组件与画稿 QA

- 是否读取主页面已有 component / component set、实例、main component 和 variant properties。
- 是否明确每个状态的生成方式：原组件覆盖 / 补充 variant / 结构扩展 / 仅进矩阵。
- 是否判断补充 variant 应进入哪个原父 component set。
- 结构变体是否在生成前明确参考源、保留区、可变区和字段来源。
- 新组件 / 替代结构是否有真实组件来源；若无可靠来源，是否已降级为仅进矩阵、低保真草稿或等待标准组件源。
- 组件来源是否同时满足视觉体系、结构槽位和使用语境三要素；manifest key 或图标 key 不能单独作为正式高保真来源。
- 是否避免用手绘近似稿替代已有组件实例。
- 颜色、按钮、文字链、分隔线、圆角、间距是否来自原组件、原页面或本 skill 内置的 Figma 设计系统 manifest。
- 是否优先复用 `manifests/components-manifest.json` 中的 component set / variant，而不是手绘替代。
- 图标是否来自 `manifests/icons-manifest.json`。
- 是否已运行 `python3 scripts/validate_figma_brief.py brief.json` 且 PASS。
- 补全 Section 是否使用默认深色中性背景，状态说明是否使用浅色文字且清晰可读。
- 写入 Figma 时是否创建在原文件新 Section，且没有覆盖原主页面。
- `target.reference_node_id` 是否只作为参考定位节点，没有被用作生成节点的父容器。

## 3. 布局与内容 QA

- 模块状态是否放回真实页面 / 父容器中；若是孤立模块，是否为用户明确要求的模块态。
- 上下文切换状态是否清除了旧上下文附属结构；不得只替换局部内容而残留旧路径、旧步骤、旧筛选、旧 Tab 内容或旧行动入口。
- 字段、价格、按钮、标签、图标和说明文案是否仍停留在正确槽位，没有跨子结构迁移。
- 字段业务角色是否正确；不得只按视觉位置、文本长度或节点名称相似做字段硬对标。
- 数量边界是否做了合理布局重排，而不是机械删除、拉宽或缩放。
- 数量边界是否已由 skill 自动推导布局策略；不得因状态输入表未提供卡片尺寸、布局比例或上移距离而跳过判断。
- 内容减少后，是否重新评估单个元素内部布局；若出现无效空白、内容集中在左上角、关键字段未同行聚合或模块高度未收缩，必须判为不合格并改成结构变体。
- 数量边界在完整页面固定宽父容器内，是否已明确父容器策略；不得只收缩子模块后在原行留下明显右侧空白。
- 父容器已占满时，是否继续检查卡片内部密度；单卡或少卡状态若图片 / 文本之外空白过大、信息区过轻、卡片高度沿用多卡高度，必须判为不合格。
- 结构变体是否建立视觉组和对齐轴；不得只检查单节点宽高、文本非空和父容器边界。
- 删除旧槽位后，父容器高度、服务列表起点和下方页面流是否同步收缩或顺延。
- 少项内容是否尊重父级信息阅读轴；信息卡、会员卡、订单卡、列表卡等左侧扫描结构中，1 / 2 项默认居中且未同步收缩父容器时，应判为不合格。此检查针对内容单元在父容器内的排布位置。内容单元内部元素的对齐方式（如标题组、装饰组的居中或左对齐）属于内部布局问题，应按结构变体的内部布局推导结果判断，不按此条容器级规则判定。
- 空状态是否删除无意义空容器，或按规范保留占位。
- 超长文案是否真实触发换行、截断或溢出边界。
- 价格、按钮、优惠标、说明文案等强关联元素是否仍保持原稿的对齐轴和垂直关系；新增内容不得形成孤立的右下角块、悬空空洞或与价格区脱节。
- Figma 中截图可见的基础对齐问题、文字压线、重叠、裁切、明显空洞，必须在 V1 写入后立即修复。
- 页面流顺延时，是否移动所有后续对象和依附对象。
- 固定底 bar、悬浮入口、安全区是否没有被误当作页面流内容移动。
- 完整页面组合态是否同时检查目标模块局部、父容器整行和整页可见区域。
- 完整页面组合态中，稳定区可随页面态重复出现作为上下文，但 QA 的变更检查必须限定在目标变化区及其承接链路；不得把稳定区重复输出误判为额外业务改动。
- 参考基线态和变体态必须分开验收。基线态只验证与参考稿一致和上下文完整；变体态才应用结构重排、数量边界、模块高度收缩和页面流顺延规则。

## 4. 四道 QA 门禁

全部通过后才允许交付；任一门禁失败，都必须修复、降级或阻断。

### 语义 QA

- 状态名、触发条件、用户含义和矩阵 / 状态表一致。
- 上下文切换完整，旧语境文案、路径、筛选、CTA 没有残留。
- 字段语义角色一致，不同层级信息没有混放。
- 不生成未确认状态，不混入平台异常或低层交互状态。
- 业务域特定字段归属按 `references/domains/<业务域>.md` 检查（如有）。

### 结构 QA

- 模块状态是否放回真实页面 / 父容器中；若是孤立模块，是否为用户明确要求的模块态。
- 页面态中的稳定上下文是否保持稳定；仅目标变化区及其直接父容器、后继页面流、固定区外层允许随状态变化。
- 目标锚点、输出 Section、所有状态页 / 状态模块是否拥有同一个 Page 祖先；不得只凭 `getNodeById` 非空或 Section 名称判断写入位置正确。
- 若本次发生过 `ok:false`、脚本内置 QA 失败或重试写入，是否确认没有错误 Page、错误 Section、半成品状态页或空壳 Section 残留。
- 字段进入正确槽位，图标、标签、价格、按钮、提示没有跨槽位。
- 新增结构位于正确层级。
- 标为删除的旧槽位不可见，标为替换的槽位仍保持同层级和同业务角色。
- 删除槽位后父容器高度、列表 y 起点、下方内容位置完成同步调整。
- Auto Layout 子节点顺序、gap、padding 没被破坏。
- Auto Layout sizing 没被静默退化：参考稿为 Fill / Hug / Auto resize 的关键容器、信息组和文本，生成稿不得变成 Fixed，除非结构变体 sizing plan 明确声明并通过 QA。
- 隐藏节点不影响可见布局和可点击区域。

### 视觉 QA

- 图标风格、字号、字重、行高、基线与原体系一致。
- 文本不压线、不裁切、不误换行、不空白显示。
- 价格、单位、按钮、标签、提示与原稿对齐轴和间距一致。
- 卡片密度、留白、圆角、背景和分隔线符合原稿。
- 新增内容没有孤立、漂浮、突兀或明显低保真感。

### 来源 QA

- 生成稿是否 clone 自参考页面、模块或原组件实例；若从空白重建，是否有用户明确要求或可靠原因。
- 每个新组件、新图标、新结构都有真实来源。
- 组件来源同时满足视觉体系、结构槽位和使用语境。
- 新增 fill、text style、radius、spacing、padding 来自原稿或 manifest，例外需说明。
- manifest 校验只作为资源存在证明，不能替代来源适配判断。

## 5. QA 证据与截图

默认先截新 Section 全景，检查整体分组、空白、错位和明显视觉问题。

视觉校准和截图验收默认使用 `get_screenshot`。不得为了普通视觉目检调用 `get_design_context`；只有任务同时需要设计到代码上下文、组件代码参考或 MCP 明确要求时，才使用 `get_design_context`。

只有发现问题、内容密度高、存在裁切风险或结构变体复杂时，再截单个状态或目标模块局部。不得默认对每个状态都做高分辨率截图，除非状态结构不同或风险高。

写入型任务交付前必须保留：

- 参考源截图或关键节点 ID。
- 生成结果截图。
- 目标锚点、输出 Section、状态页 / 状态模块的 Page 祖先一致性证据。
- 若发生过失败写入或重试，失败批次残留清理证据。
- 关键槽位映射和节点 / 组件来源。
- 语义、结构、视觉、来源四类 QA 的问题清单。
- 修复后问题清零结论。

## 6. 异常状态 QA

仅当用户明确要求 loading、骨架屏、空态等异常状态时检查：

- 是否读取平台规范源文件或设计系统源节点，而不只是导入单个示例组件。
- 平台状态是否有标准来源；没有标准来源时不得输出正式高保真稿。
- 是否只生成用户需要的基础状态，没有扩写无关异常态。
- 骨架态是否保留原模块容器、内边距、标题区、列表区、列间距和元素边界。
- 失败态和兜底态是否复用原入口、原容器和原行动区。
- 规范色在当前背景不适配时，是否做了有说明的语境映射。

## 7. 高频失败模式

### 矩阵主轴错位

表现：用户要求补某个子结构，矩阵却按抽象业务标签命名。
检查：状态名称是否能映射到具体节点、字段、组件或业务变量。

### 非法组合未过滤

表现：生成业务上不可能同时出现的组合，或忽略数量上限。
检查：每类变量是否记录数量上限和互斥关系，不适用组合是否在矩阵阶段过滤。

### 排布能力和展示能力混淆

表现：看到 wrap 就默认增高展示全部内容，忽略固定高度和裁切。
检查：容器是否固定高度，是否 clipsContent，下方模块应保持还是顺延。

### 空状态留白

表现：子结构无内容，但保留原高度形成空白行。
检查：是否有占位规范；无占位要求时是否删除空容器并检查下方布局。

### 数量减少后机械拉伸

表现：只删除多余元素并拉宽剩余卡片，内部内容仍沿用多元素状态的纵向堆叠，导致右侧 / 下方大面积空白。
检查：先判断剩余元素内部信息是否需要重排；宽度增加时，强关联字段应优先同行聚合。

### 布局策略缺失

表现：状态输入表只写了 1 排 2 / 1 排 1，生成时没有根据 Figma 参考稿自动判定卡片宽高、图片 / 文本比例、模块高度和页面流联动，只做删除或拉伸。
检查：数量边界状态写入前必须有内部布局策略判定；常规布局执行问题不应要求用户在状态输入表中补字段。只有产品决策或结构归属存在不可消解分歧时才暂停询问。

### 数量边界父容器留白

表现：生成 1 排 2 / 1 排 1 等少项状态时，子模块或子卡片已减少，但完整页面的原固定宽父容器仍留下大片右侧空白。
检查：写入前明确父容器策略；截图 QA 同时检查目标模块局部和父容器整行。若空白大于一个原卡片宽度或没有业务占位说明，必须改成适配父容器宽度的结构变体、同步收缩父容器并联动页面流，或只生成模块态。

### 父容器占满但低密度大卡

表现：少项状态的卡片右边界已填满父容器，但卡片内部信息很少，图片和文字之外存在大片空白，模块高度仍沿用多卡状态。
检查：父容器无右侧空白只是必要条件，不是充分条件。继续检查卡片内部空白、文本真实行数、图片区 / 信息区比例、卡片高度和模块高度；若文本可单行或少行展示，应收缩信息区、卡片和模块高度，并同步处理下方页面流。

### 结构变体缺少视觉组建模

表现：结构变体生成后，单个节点的尺寸、文本和父容器边界看起来都正确，但主视觉组、主信息组、辅助信息组、操作组或状态组之间漂浮、偏移、错轴或阅读顺序不稳定。
检查：写入前必须识别视觉组、组内阅读轴和组间对齐轴；写入脚本应使用 `scripts/layout_visual_groups.js` 或等价 helper 计算组包围盒，并返回 `layoutQa`。若只看到孤立坐标硬编码或没有组级 QA，判为不合格。

### 孤立坐标导致组间错位

表现：结构变体中单个节点使用固定 `x/y` 偏移移动，局部看似正确，但相邻视觉组没有按共同轴线对齐。
检查：坐标必须来自父容器、视觉组或相邻组的包围盒计算。QA 应检查组级 center / leading / trailing / inside-parent 关系，而不是只检查文本不裁切。

### 容器级规则误覆盖内容单元内部布局

表现：结构变体中，内容单元内部的元素对齐被容器级阅读轴规则覆盖，例如本应居中的标题装饰组被改为左对齐，或本应横向排列的信息组被改为纵向堆叠。
检查：容器级排布规则（如"左侧阅读轴""不得默认居中"）的适用对象是内容单元在父容器内的位置，不是内容单元内部元素。内部元素对齐应基于结构变体的新形态独立推导。若 QA 发现初始写入的内部对齐合理但被后续"修复"改坏，应回退修复。

### 少项状态错误居中

表现：内容减少到 1 / 2 项后，剩余元素被放到卡片中间，破坏原信息阅读轴。
检查：确认父级是否为信息流卡片；若是，少项内容应优先沿左侧起始轴紧凑排列。

### 组件复用被手绘替代

表现：原组件存在，却手工重画标签、徽标、按钮或图标。
检查：关键子元素是否仍是原实例、原组件变体，或来自 manifest 的导入实例。

### 新结构无来源自创

表现：参考稿和设计系统中没有对应组件，仍直接画出看似正式的新卡片。
检查：该状态是否属于新组件 / 替代结构；没有来源时是否降级为仅进矩阵或低保真草稿。

### 上下文切换残留

表现：状态语境已经变化，但旧语境的路径、筛选、Tab 内容或行动入口仍保留在画稿中。
检查：生成后是否逐项读取节点确认旧上下文没有残留。

### 字段跨槽位迁移

表现：一个子结构的字段被迁移到另一个子结构中，几何上不重叠但语义错误。
检查：先读取每个子结构的字段槽位；生成后按槽位而不是按全文搜索验证字段归属。

### 字段角色错用

表现：把一个槽位当成“相似文本容器”复用，但字段业务角色不一致。
检查：视觉位置相似、字号相同、节点名称相近都不能替代字段角色判断。业务域特定字段角色按 `references/domains/<业务域>.md` 检查。

### 关联结构脱离原槽位

表现：新增优惠标、权益标、价格说明等子结构没有进入原组件槽位，在画板角落独立悬浮。
检查：先读取原组件内部槽位；能 override 原实例时必须 override 原实例。

### 稳定字段误改

表现：误改房型名、店铺名、价格、CTA 或固定区域。
检查：生成前列出稳定字段，QA 对比主态和补充态。

### Manifest 校验被跳过

表现：画稿写入成功但颜色、圆角、字号、图标或组件来源不明。
检查：是否生成 brief 并通过 `validate_figma_brief.py`；若走 clone-first 脚本，也必须说明新增资源来源。

### 误写原主页面

表现：生成节点被 append 到原主页面、原模块或原组件内部。
检查：原参考节点是否没有新增、移动、删除或覆盖。

### Variant 切换失败

表现：切换 variant 后宽度未跟随、文本叠字、样式错乱。
检查：切换后截图检查节点宽高和内部文本。

### 文案 Override 失败

表现：脚本写入后截图仍显示原文、重复文案或字体为空。
检查：写入前加载字体，写入后读取 text.characters 或截图确认。

### 几何值通过但视觉失败

表现：x/y/w/h 正确，但截图仍有空白、空洞、孤行、叠字。
检查：关键状态必须截图 QA，截图目标必须是真实 Frame / Instance / Component。

### 自适应布局退化为固定尺寸

表现：生成稿仍是 Auto Layout，但单模块、卡片、信息组或文案从参考稿的 Fill / Hug / textAutoResize 变成 Fixed，导致后续改文案或数量时出现对齐偏差、空白、裁切或不可维护。
检查：深读参考节点时记录 `layoutSizingHorizontal`、`layoutSizingVertical`、`primaryAxisSizingMode`、`counterAxisSizingMode` 和 `textAutoResize`；写入后用 `autoLayoutQa` 对比。未声明原因的 Fill / Hug / Auto resize → Fixed 视为失败。

### 批次通过后退化

表现：小范围生成质量可接受，全量生成同一状态时质量下降。
检查：已通过状态是否作为回归基线；发现退化时是否阻断后续批次。

### 交付假完成

表现：画稿已写入 Figma，但基础 UI 问题未清零，最终仍回复“已完成”。
检查：QA 问题清单是否为空；若存在问题，是否选择修复、降级或阻断。

## 8. 失败最小修复

失败后只读取错误相关路径，避免重新大范围读取。每次修复前先标明失败类型和本次读取范围。

修复脚本只返回：

- 修复对象
- 修复动作
- 剩余 failures
- 是否清零

不得返回完整节点树、完整 stateSummaries 或无关状态几何。

若失败暴露出写入前门禁遗漏，必须回到矩阵 / 状态表确认阶段，不得用写入后说明补救。

## 9. 最终回复 QA

- 是否包含补全规模：已补全状态数、已画稿数、仅进矩阵数、不适用组合数。
- 是否只列最多 5 条重点变化。
- 是否避免在最终回复中完整复述状态矩阵。
- 写入型任务中，是否没有在最终回复新增会改变状态矩阵、模块是否需要、展示内容、CTA、页面结构或字段显隐的人工确认问题。
- 若存在影响写入结果的疑问，是否已在 Figma 写入前集中询问并等待用户确认。
- 写入型任务是否已完成语义、结构、视觉、来源四道 QA，且问题清单已清零。
- 若基础 UI 问题未清零，最终回复是否明确说明阻断、降级或待修复，而不是声称完成。
