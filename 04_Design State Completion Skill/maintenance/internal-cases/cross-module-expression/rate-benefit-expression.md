# 样例：酒店详情页 88VIP rate 权益强化表达

## 背景

页面业务背景是酒店详情页 rate 卡片中的 88VIP 权益强化表达。主页面已经给出房型 rate 在 `88VIP 免费早餐` 和 `88VIP 无忧退` 两类权益下的 before / after 设计，需要补齐普通 rate 的相同权益表达。

该案例属于酒店域中的 rate 权益表达，重点不是新增页面状态，而是把同一权益规则迁移到另一个已有组件类型中。

## 主页面输入

主页面包含：

- 房型 rate / 免费早餐 / before
- 房型 rate / 免费早餐 / after
- 房型 rate / 无忧退 / before
- 房型 rate / 无忧退 / after

组件区包含：

- 房型 rate component set
- 普通 rate component
- rate / 早餐
- rate / 退改政策
- rate / 运营坑标
- rate / X项
- rate / 大促标
- rate / 紧迫感

## 人工全情况目标

补全重点：

1. 普通 rate / 免费早餐 / before。
2. 普通 rate / 免费早餐 / after。
3. 普通 rate / 无忧退 / before。
4. 普通 rate / 无忧退 / after。

## 状态矩阵

| rate 类型 | 权益类型 | 阶段 | 关键变化 | 生成方式 |
| --- | --- | --- | --- | --- |
| 普通 rate | 免费早餐 | 权益前 | 早餐展示普通早餐，运营坑标展示里程抵扣 | 复制普通 rate 原组件实例 |
| 普通 rate | 免费早餐 | 权益后 | 早餐字段变为 `88VIP可兑免费早餐`，运营坑标切到 88VIP 权益样式 | 复制普通 rate 原组件实例并 override |
| 普通 rate | 无忧退 | 权益前 | 退改政策保持常规可取消，运营坑标展示无忧退 | 复制普通 rate 原组件实例 |
| 普通 rate | 无忧退 | 权益后 | 退改政策文案强化为 `88VIP无忧退·入住当天20点前可免费取消` | 复制普通 rate 原组件实例并 override |

## 生成规则

- 不要复制房型 rate 的结构来画普通 rate。
- 必须以普通 rate 原组件为基底。
- 权益表达迁移时，要先找目标组件里的等价承载字段。
- 免费早餐优先落在 `rate / 早餐`，再同步 `rate / 运营坑标`。
- 无忧退优先落在 `rate / 退改政策`，再同步 `rate / 运营坑标` 或服务标签。
- 酒店店铺名、价格结构、按钮样式、服务标签基础样式是稳定字段，不应因为权益状态而误改。

## 对比复盘结论

从主页面、组件区和手动全情况稿对比得到：

- 同一业务权益在不同 rate 类型中应形成横向补齐矩阵：`rate 类型 × 权益类型 × before/after`。
- 当主页面只给出房型 rate 的权益表达时，skill 应主动检查普通 rate 是否也是同域核心组件，而不是等待用户点名。
- 补齐普通 rate 时，组件复用比视觉模拟更重要；即使手动稿看起来只是普通 frame，也应追溯其 main component。
- Figma Section 不适合作为截图承载目标时，应改用 Frame 输出可渲染闭环，避免截图只有空白底。

## 最终验收结论

最终交付不应只输出“普通 rate 补充区”，而应把主页面已有房型 rate before / after 与补齐的普通 rate before / after 合并成整体矩阵。

推荐矩阵：

- 横轴：免费早餐 / 权益前、免费早餐 / 权益后、无忧退 / 权益前、无忧退 / 权益后。
- 纵轴：房型 rate、普通 rate。

确认规则：

- 普通 rate 无忧退后态的运营坑标保持 `F4 无忧退`，强化表达落在 `rate / 退改政策` 文案。
- 已完成的主页面状态也必须进入矩阵，不能只展示新补齐状态。

经验：

- 补充变体必须并入原父组件，组件系统才完整。
- 页面状态标注优先用纯文字。
- 原模块是 auto layout 时，不能只设置位置，还要检查子节点顺序。
