# Figma 生成规则

<!-- scope: Figma 写入前确认、写入边界、画布输出、组件复用、命名规则 -->

## 0. 设计系统来源

写入 Figma 的视觉规范、组件规范、图标规范和变量规范以本 skill 内置的 Figma 设计系统 manifest 为准：

- `tokens-mapping.json`：颜色、间距、圆角、文字样式和 effect 的 Figma variable/style 映射。
- `components-manifest.json`：Figma component set、variant、分类和搜索索引。
- `icons-manifest.json`：Figma 图标库索引。

业务域变量和状态判断按对应的 `domains/<业务域>.md`（如有）执行；画稿视觉和组件落地必须使用上述 Figma manifest。

写入 Figma 必须走 manifest-driven brief 链路：

1. 生成 `brief.json`，其中 `target.file_key`、`target.reference_node_id`、`target.section_name` 必填。
2. 使用 `tokens-mapping.json` 选择颜色、间距、圆角、文字样式和 effect。
3. 使用 `components-manifest.json` 复用 component set / variant。
4. 使用 `icons-manifest.json` 复用图标。
5. 运行 `python3 scripts/validate_figma_brief.py brief.json`，FAIL 必须修到 PASS。
6. 运行 `python3 scripts/compose_figma_section_code.py brief.json --out /tmp/write.js`。
7. 调用 `use_figma(fileKey=<target.file_key>, code=<contents of /tmp/write.js>, description=...)` 写入新 Section。

禁止为了视觉相似手绘替代 manifest 中已有的 component、icon、text style、spacing、radius 或 fill token。

## 1. 写入边界

- 写入 Figma 前必须使用 `figma-use` skill。
- 只有用户明确要求写回 Figma、直接生成画稿、补全设计稿或同等意图时，才写入用户提供的原 Figma 文件。
- 写入前必须确认目标 file / node、补全区域名称和写入范围。
- 探索式推导模式下，写入 Figma 前必须完成 `state-decision-framework.md` 的状态范围确认和 `state-matrix-rules.md` 的候选状态确认。规格驱动模式下，状态范围由用户提供的状态表确定，不需要矩阵推导，但仍需完成参考稿结构解读（第 1.6 节）。
- 写入前必须集中完成所有影响画稿结果的人工确认：状态矩阵取舍、模块是否需要、展示内容判断、CTA、页面结构、字段显隐、关键业务规则和不适用组合。不得先写入，再在最终回复中询问这些问题。
- 不覆盖原主页面，不改动与本次补全无关的原节点。
- `target.reference_node_id` 只作为参考定位节点，不得作为 `appendChild` / `insertChild` 的父容器；所有生成内容必须写入脚本新建的 Section 内。
- 优先复制主页面、主模块或原组件实例后改造，不从空白重画。
- 如果存在设计系统组件、component set、variant 或实例，必须优先复用；不得为了"看起来相似"手绘替代。
- 写入时必须检查可加载中文字体。若 `PingFang SC` 不可加载，优先使用 `Noto Sans SC` 或当前文件中可加载的中文字体。

## 1.5 状态复杂度分级

写入前把每个状态分为三类，决定生成策略：

- 轻改状态：只改文案、字段值、显隐、状态标签或 CTA，不改变子结构。可批量生成。
- 结构变体：增删子结构、替换内容组合、改变列表数量、调整模块高度、切换上下文或影响页面流。生成前应明确参考源、保留区、可变区和字段来源。
- 新组件 / 替代结构：参考稿中没有对应结构，需要新的卡片、弹窗、搜索区或兜底模块。必须确认组件来源（见第 4 节）；没有可靠来源时不得输出正式高保真稿。

全量生成时应分批进行：生成一批，完成四道 QA（见 `quality-and-failures.md`），问题清零后再进入下一批。已通过的状态作为回归基线，后续批次不得让其退化。


## 1.6 参考稿结构解读

规格驱动生成和结构变体生成前，必须先对参考 Figma 稿做节点级结构分析，而不是只看截图。

具体做法：

- 使用 Figma MCP 的 get_file_context 或 get_node 读取参考节点的子结构树。
- 识别每个关键子结构的语义角色：Tab 栏、锚点条/信息条、服务行列表、推荐标记、价格区、CTA、辅助提示等。
- 记录哪些子结构是 component instance（可 clone + override），哪些是普通 frame（需要手动改造）。
- 如果参考稿中已有多个完成的状态（如用户同时提供了 P1 和 P2），对比它们的结构差异，作为后续生成的已知变形模式。

参考稿结构解读的产出是一份"语义地图"，列出每个子结构的节点定位、语义角色、是否稳定。这份地图是后续所有 clone + 改造操作的基础。

不要跳过这一步直接 clone 参考稿然后凭直觉改。

## 2. 画布输出模式

默认启用轻量画布输出模式。Figma 画布只承载用户需要验收的设计结果，不写入完整推理过程。

每次生成的所有内容必须维持在同一个 Section 内，命名为 `业务状态补全 / {页面名称}`。

Section 背景默认使用深色中性背景，推荐 `#2B2B2B` 或沿用当前文件同类补全 Section 的深色背景；不因原页面浅色或深色背景而改变。状态画板自身背景必须保持原稿真实背景，不因 Section 背景统一而修改。

默认 Section 内容只包含新生成的状态画板、模块状态或组件变体，以及每个状态画板上方的简短状态说明。即使命中"状态矩阵推演"能力，状态矩阵也只作为写入前的内部推演和确认材料，不在 Figma 画布中生成矩阵标题、描述、表格或不适用组合说明。

默认不要在画布中额外生成可见标题、说明区或重复说明文本。Section 名称、画稿节点名称、补全范围、能力路由和 QA 过程只作为 Figma 图层命名或内部推理信息。

如果用户在写入前是按 A / B / C 状态类型分组确认的，Figma 写入时也必须按同样分组排布，让用户能看出哪些属于业务全状态、内容边界状态、异常状态。分组方式优先使用以下任一方式：

- 在同一个 Section 内按 A / B / C 分成清晰的行、列或区块，并保持组内状态连续排列，不要把不同分组交错混排。
- 每个分组前可添加一行轻量分组说明文字，例如 `业务全状态`、`内容边界状态`、`异常状态`；分组说明只用于区分区域，不替代每个状态画板上方的状态说明。
- 如果只选择了一个分组，可以不额外添加分组说明，但仍需保持该分组内状态连续。

分组说明不得使用用户确认表里的 `A` / `B` / `C` 编号作为主要标题；可用中文类别名，必要时在图层命名中保留编号。

按需 Section 内容：

- `01 页面级场景`：仅在页面级状态需要完整页面承接时写入。
- `02 核心模块全情况`：仅在模块状态需要集中验收时写入。
- `03 结构变体`：仅在结构确实变化时写入。
- `04 子组件变体`：仅在创建或补齐 component / component set 时写入。

## 3. 命名和状态说明

所有节点命名使用中文；单个状态画稿命名不添加 `html` / `html2` 等固定字母前缀，不映射真实地址、URL 或页面链接。

单个状态画稿命名：

- 页面级：`页面名称 / 状态名称`，例如 `会员挑战页 / 挑战中`。
- 模块级：`模块名称 / 状态名称`，例如 `权益卡片 / 已领取`。

子结构级和字段级暂不新增命名规则，按当前任务最贴近的页面级或模块级承载对象命名。

状态说明节点命名：`状态说明 / {状态名称}`。

每个状态画板必须配套一个简短状态说明。轻量画布模式下，状态说明是状态画板上方唯一默认可见的说明文本。

说明格式：`{状态名称}：{核心变化}`，或在确实需要触发语境时使用 `{状态名称}：{简短触发语境} / {核心变化}`。

状态说明文案不得带用户确认阶段的编号，例如 `A1`、`A2`、`B1`、`C1`。编号只用于用户选择和内部追踪；写入 Figma 时，状态说明和画稿可见名称都应使用纯状态名称。

状态说明位置：

- 放在对应状态画板上方，与画板左边缘对齐，保持 8-12px 间距。
- 不遮挡画稿内容，不使用装饰性标签或大卡片。
- 在默认深色 Section 背景上，状态说明必须使用浅色文字，推荐 `#F5F5F5`；辅助说明可用 `#D0D0D0`。不得使用接近黑色的文字导致不可读。

不要额外生成以下可见文本：

- Section 标题，例如 `业务状态补全 / {页面名称}`。
- 画稿标题，例如 `页面名称 / 状态名称` 或 `模块名称 / 状态名称`。
- 状态矩阵标题、状态矩阵表格、状态矩阵描述或不适用组合说明。
- 能力路由说明。
- 补全范围说明。
- QA 过程说明。
- 与状态说明语义重复的大段解释。

## 4. 组件复用和画稿规则

- 保持原页面视觉语言：颜色、圆角、字体层级、按钮、图标、徽标、标签、分隔线、间距应来自原稿或原组件。
- 业务稳定元素不要随状态变化，例如挑战名称、任务标题、奖品名称、会员等级名称、酒店名、房型名、店铺名、基础价格结构。
- 业务状态变化要体现在 CTA、文案、状态标签、模块显隐、利益点表达或流程反馈中。
- 组件来源优先级：① 当前 Figma 文件中的真实节点或组件实例 → ② 已订阅组件库中的组件 → ③ 用户提供的规范源 → ④ 当前主页面中可合法改造的原槽位。找不到组件源时，不得输出正式高保真稿；可降级为低保真草稿并标注。
- 组件复用必须满足视觉体系、结构槽位和使用语境三要素；不得只因为存在 manifest key 或视觉相似节点就把它当作正式来源。
- 当用户要求"直接生成为子组件"时，必须创建或补齐 Figma component / component set，而不是只画普通 frame。
- 补充 variant 必须和原变体放在同一个父 component set 内；可标注 `来源=原组件` / `来源=补充`，但不要分散成两个无关组件区。
- 对复合模块，应先拆子组件，再列页面组合态。不要把所有状态都塞进一个大组件矩阵。
- 页面组合态中的状态说明必须放在对应画板上方，并优先用纯文本。
- 输出后必须完成语义、结构、视觉、来源四道 QA。截图检查不仅检查中文文本是否缺字、裁切或显示为空，还必须检查对齐、基线、密度、图标风格、槽位语义和正式稿质感。QA 问题清单非空时不得交付完成。
- 结构变体、数量边界、横纵布局切换和模块高度变化的写入脚本，应优先嵌入或等价实现 `scripts/layout_visual_groups.js`。必须以视觉组包围盒和对齐轴计算布局，并在 use_figma 返回值中包含 `layoutQa`；不得只用孤立坐标硬编码完成改造。

### 4.1 结构保真与 Auto Layout 保留

- 参考稿关键容器若 `layoutMode != "NONE"`，生成稿对应容器也必须保持 Auto Layout。关键容器包括页面流容器、模块容器、列表 / 栅格容器、卡片容器、信息组、标题行、CTA / 操作组和其他设计师会继续编辑的结构层。
- 结构变体可以按布局策略在 `HORIZONTAL` 和 `VERTICAL` 间切换，但不得退化为 `NONE` 后只靠 `x/y` 坐标模拟。方向切换必须在布局策略和 QA 返回值中说明。
- 子节点顺序、`padding`、`itemSpacing`、`layoutSizingHorizontal`、`layoutSizingVertical`、`primaryAxisSizingMode` 和 `counterAxisSizingMode` 应优先沿用参考稿；确需改变时必须服务于结构变体，而不是写入脚本省事。
- 图片裁切层、装饰矢量、蒙版、固定浮层、原本就是绝对定位的标签等，可保持非 Auto Layout；但不得把可编辑的信息结构层、列表层或卡片层整体降级为普通 frame。
- 结构变体写入脚本应嵌入或等价实现 `scripts/auto_layout_qa.js`。写入后必须返回 `autoLayoutQa`，并至少检查关键容器的 `layoutMode`、方向变化、子节点绝对定位比例和退化失败清单。
- `layoutQa` 通过但 `autoLayoutQa` 失败时，仍视为不可交付。必须修复 Auto Layout 结构、明确降级为低保真，或阻断交付。

复杂场景按需读取：

- 页面级状态、列表顺延、固定底栏、依附标签和内容边界：`layout-composition-rules.md`
- loading、骨架屏、空态等异常状态：`platform-state-rules.md`

## 5. 状态矩阵写入规则

状态矩阵必须先于画稿生成，但只作为内部推演产物和写入前确认材料，不写入 Figma 画布。

状态矩阵也是写入前人工确认门禁：凡是会改变是否画稿、模块构成、展示内容、CTA、页面结构或字段显隐的不确定项，必须在矩阵阶段问清楚；不得作为写入后的待确认问题。

Figma 写入结果不得包含状态矩阵标题、状态矩阵描述、矩阵表格或不适用组合说明；画布只保留生成的状态设计稿和每个状态对应的简短状态说明。

内部状态矩阵基础字段：状态名称、触发条件、核心变化、生成方式、是否画稿。

复杂业务可增加：状态类型、用户含义、页面变化、主 CTA、优先级、假设说明。
